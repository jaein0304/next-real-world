## Context

Next.js 12 + React 18 + Prisma 4 (MySQL) + Apollo Server/Client + Nexus + Tailwind CSS 3 기반 풀스택 RealWorld 블로그 앱. 코드 분석 결과 7개 DB 모델, 4개 query 그룹, 4개 mutation 그룹, 11개 페이지, 58개 컴포넌트, 8개 커스텀 훅으로 구성. OpenSpec `openspec/specs/` 디렉토리는 현재 비어 있음.

## Goals / Non-Goals

**Goals:**
- 프로젝트의 모든 주요 capability를 OpenSpec 형식으로 정확하게 문서화
- 각 스펙이 테스트 가능한 시나리오(WHEN/THEN)를 포함하여 향후 테스트 작성의 기준 제공
- AI가 스펙을 읽고 프로젝트 구조를 즉시 이해할 수 있도록 명확하고 구체적으로 작성

**Non-Goals:**
- 코드 변경 또는 리팩토링
- 미래 기능에 대한 요구사항 정의 (현재 구현된 것만 문서화)
- API 문서 자동 생성 도구 도입

## Decisions

### 1. Capability 분류 기준

**선택**: 아키텍처 계층 + 도메인 기준으로 8개 capability로 분류

```
                    ┌─────────────────────┐
                    │   dev-tooling       │  ← 횡단 관심사
                    └─────────────────────┘
┌──────────┐  ┌──────────┐  ┌───────────────┐
│  pages   │→ │components│→ │  validation   │  ← 프론트엔드 계층
│ -routing │  │          │  │               │
└──────────┘  └──────────┘  └───────────────┘
        │           │
        ▼           ▼
┌───────────────────────────┐
│   frontend-architecture   │  ← Apollo Client, 상태, 캐시
└───────────────────────────┘
              │
              ▼
┌──────────┐  ┌──────────┐  ┌───────────────┐
│ graphql  │→ │  auth    │→ │  data-model   │  ← 백엔드 계층
│  -api    │  │entication│  │               │
└──────────┘  └──────────┘  └───────────────┘
```

**근거**: 각 capability가 독립적으로 이해 가능하면서, 의존 관계가 명확하게 드러남.

### 2. 스펙 작성 깊이

**선택**: 현재 코드에 구현된 정확한 동작을 문서화. 필드명, 타입, 제약조건 등 구체적인 값 포함.

**근거**: 학습 프로젝트이므로 구현 세부사항이 곧 학습 자료. 추상적 요구사항보다 구체적 구현 명세가 더 유용.

### 3. 시나리오 작성 방식

**선택**: 각 Requirement에 핵심 시나리오 1~3개, WHEN/THEN 형식으로 작성. 향후 테스트 케이스로 직접 변환 가능한 수준.

**근거**: vibe-coding-transition의 테스트 인프라 구축(Phase 2)에서 이 시나리오들이 테스트 케이스의 기초가 됨.

### 4. 메인 스펙으로 직접 생성

**선택**: delta spec이 아닌 `openspec/specs/<capability>/spec.md`에 직접 메인 스펙 생성

**근거**: 기존 스펙이 없으므로 delta → sync 과정 불필요. 직접 메인 스펙을 생성하는 것이 효율적.

## Risks / Trade-offs

| Risk | Mitigation |
|------|-----------|
| 코드와 스펙이 시간이 지나면 불일치 | 코드 변경 시 OpenSpec change로 delta spec 업데이트 프로세스 운영 |
| 8개 capability가 과도한 세분화 | 각 스펙이 독립적으로 읽히도록 작성하되, 필요 시 통합 가능 |
| 현재 코드의 버그/의도치 않은 동작도 스펙에 포함될 수 있음 | 명확한 버그는 제외하고, 의도된 동작만 문서화 |
